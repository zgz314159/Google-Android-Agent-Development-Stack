## 2. Fix A — Hermes-aware Auto-Finalizer

### 2.1 Before / after

| | Before (S1) | After (S1.1) |
|---|---|---|
| Execution sources | `commandcode` only | `commandcode` **and** `hermes` |
| Discovery | `~/.commandcode/projects/*/*.jsonl` | + completed Hermes ROOT sessions in `state.db` |
| Trigger | systemd timer → `scan` (2 min) | + thin `on_session_finalize` shell hook (observer-only, detached one-shot) |
| Recovery | `replay --session <jsonl>` (CC only) | + `scan --source hermes` sweep and `hermes-session --session-id X` backfill |
| Index record | `mtime_ns,size,run_id,output_dir,session_id` | + `source,source_type,fingerprint,finalized_at` (additive) |
| Evaluation Core | v0.2.3 | v0.2.3 **unchanged** (no second evaluation system) |

The design is a **source abstraction**, not a second finalizer:

```
Execution Source (commandcode | hermes)
        ↓  normalized session metadata
Auto-Finalizer (auto_finalize.py)
        ↓
Evaluation Core / canonical report (core.analyze -> run.json, phase-timeline.csv, analysis.md, finalization.json)
```

### 2.2 The thinnest integration point (reused, not rewritten)

- `hermes_session_source.py` (new, ~350 lines) reads `state.db` read-only and normalizes a
  Hermes session into a **Command Code JSONL v3 shim** (`type=session` + `version=3`; message
  rows carrying `message.meta.source` = `user|model|tool`), the only shape `core.load_session`
  accepts.
- `finalize_session.finalize()` is called **unchanged** (one additive optional kwarg,
  `execution_source`, which is omitted on the Command Code path so its `finalization.json`
  is byte-identical to v0.2.3).
- `auto_finalize.py` gained `scan --source {commandcode,hermes,all}` and a
  `hermes-session` one-shot subcommand.

Mapping used (real Hermes schema, read from the pinned install):

| Hermes | CC-v3 shim | meaning |
|---|---|---|
| `messages.role='user'` | role `user`, `meta.source="user"` | independent task prompt |
| `messages.role='assistant'` | role `assistant`, `meta.source="model"`, parts `text` + `thinking` + `tool_use` (from `tool_calls`) | assistant turn / call |
| `messages.role='tool'` | role `user`, part `tool_result{tool_use_id}`, `meta.source="tool"` | tool result (same-task continuation) |
| `sessions.started_at` (epoch s) | session header `timestamp` (ISO ms) | session open |

### 2.3 Hermes trigger mode

**HERMES TRIGGER: BOTH** (primary = session-end hook; always-available = source adapter).

Verified against the **local pinned source** (no guessing):

| Event | Fire site (pinned `vgit.af90026`) | Payload | Id field |
|---|---|---|---|
| `on_session_finalize` | `hermes_cli/lifecycle.py::finalize_session`; reached from CLI teardown, **one-shot CLI exit** (`hermes_cli/cli_shutdown.py::_finalize_single_query` → `_notify_single_query_session_finalize` → `_notify_session_finalize`), TUI, gateway | `session_id`, `platform`, optional `reason` | `session_id` |
| `on_session_end` | `agent/turn_finalizer.py:781` (every turn finalization) | `session_id`, `task_id`, `turn_id`, `completed`, `failed`, `interrupted`, `turn_exit_reason`, `model`, `platform` | `session_id` |

`on_session_finalize` was chosen (once per session, not per turn). The hook is a shell hook
declared in the profile `config.yaml`:

```yaml
hooks:
  on_session_finalize:
    - command: "/mnt/AndroidDev/Projects/Google-Android-Agent-Development-Stack/orchestration/hermes/evaluation_adapter/hooks/hermes-autofinalizer-hook.sh"
      timeout: 15
```

Hook script: extracts `session_id` from the stdin JSON payload (`session_id` is a promoted
top-level key in the shell-hook wire format), launches
`auto_finalize.py hermes-session --session-id <id>` **detached** (`setsid nohup`), prints
nothing (observer-only, cannot block a tool call). **No new long-running polling daemon was
added** — `watch` remains the Command-Code-only cheap poller and is unchanged.

Configuration method (deliberate, documented, reversible): the Hermes file-edit guard
refuses agent writes to the privileged `config.yaml`, so the hook was registered through
Hermes's own sanctioned interface (`hermes config set hooks ...`), and consent was granted
through the **documented manual-allowlisting path** for non-TTY deployments
(`$HERMES_HOME/shell-hooks-allowlist.json`). Undo:

```bash
hermes hooks revoke <hook-script-path>
hermes config unset hooks
```

## 3. Fix B — reference-replay screenshot reporting gap

### 3.1 Root cause (real evidence)

S1 produced 18 PNGs across 9 runs, yet every `result.json` had
`screenshot_path = null`, `screenshot_sha256 = null`. `replay.py:218` globbed a **flat**
directory:

```python
shots = sorted(glob.glob(os.path.join(maestro_out, "takeScreenshot", "*.png")))
```

Real Maestro nests the capture four levels deep:

```
.runs/S1-postfix-003958/runs/R1-1/maestro/2026-10-05_003959/R1-HOME-SEARCH/takeScreenshot/R1-search.png
```

`maestro/takeScreenshot/` does not exist, so `shots == []`, `shot = None`, and both fields
were written as null. 18/18 PNGs were present and untouched.

### 3.2 Fix

A deterministic, recursive discovery helper (`find_screenshots`) replaces the single flat
glob; the **selection semantics are preserved exactly** (`sorted(...)[-1]`, i.e. the
lexicographically-last capture, not a temporally-last one). The flat layout still works, so
older fixtures/consumers are unaffected. The result contract and the JSON schema are
unchanged (`contracts/replay-result.schema.json` is untouched; no field added to
`result.json`). `sha256_file()` was already correct (raw bytes, 64 KiB chunks) and is reused
verbatim.

### 3.3 Verification

## 4. Fix C — fail-fast runner

### 4.1 Before / after

Before: `for fid in wanted: for i in range(1, runs+1): run_one(...)` with **no break** — R1-1
FAIL still ran R1-2, R1-3, R2-1…R3-3 (9 device runs), and the non-zero exit only appeared
after the whole batch.

After (default): the first non-`PASS` run sets `stopped_early`, records
`first_failure`/`stop_reason`, prints `FAIL_FAST stop=… executed=n/planned`, breaks out (a
plain `break`, not `sys.exit`, so the `finally` releases the device lock and `index.json` is
still flushed), and the process exits 5.

`--continue-on-fail` (new, `store_true`, matching the existing all-long-option style) is the
explicit diagnostic opt-out.

### 4.2 Additive result metadata

`index.json` (no JSON schema governs it; existing consumers read by key) gained:
`planned_runs`, `executed_runs`, `stopped_early`, `stop_reason`, `first_failure`.
`result.json` is governed by `additionalProperties: false` and was therefore **not** changed
— the offline test asserts none of the batch fields leak into the per-run result.

### 4.3 Verification

Offline fixture: stub Maestro fails run #1 and would pass runs #2–9, batch
`--flows R1,R2,R3 --runs 3` (planned = 9).

| Mode | executed_runs | planned_runs | stopped_early | exit | failure evidence |
|---|---|---|---|---|---|
| default (fail-fast) | **1** | 9 | true | 5 (≠0) | YES (`runs/R1-1/evidence/metadata.json`) |
| `--continue-on-fail` | **9** | 9 | false | 5 (≠0) | YES |

Also asserted: `runs/R1-2` was never created in fail-fast mode; `totals.fail == 1`;
`first_failure = {flow_id: R1, run_index: 1, result: FAIL}`; in diagnostic mode
`totals.pass == 8`, `totals.fail == 1`, and `runs/R3-3` exists.

## 7. Known limitations

1. **No per-turn token usage for Hermes sessions.** Hermes persists session-level totals only
   (`sessions.*_tokens`, `session_model_usage`); `messages.token_count` is NULL in the pinned
   build. Per-turn usage is reported as absent/zero — never estimated.
2. **Hermes child/subagent metrics are out of scope** in S1.1 (root sessions only). Child
   sessions are deliberately excluded from discovery.
3. **`agent_host` label.** The frozen core stamps `agent_host = "Command Code"`; the true
   source lives in `finalization.json.execution_source` and in the index. Changing the label
   would require a core change (forbidden this round).
4. **`commands.json` is still discovered flat.** The same mis-glob affects
   `parse_commands()`: Maestro's nested `commands.json` is not read, so
   `assertions_source` stays `junit` on real runs. Out of scope for S1.1 (the brief allowed
   only the screenshot discovery fix); documented so it is not mistaken for a new defect.
5. **Hook consent is manual.** Shell hooks require approval; the non-TTY allowlist entry was
   written by the documented manual path. On a fresh machine the operator must re-approve
   (or run with `--accept-hooks`).
6. **The Hermes shim is a transcript copy.** `<output-root>/_hermes_staging/<session_id>.jsonl`
   (mode 0700) contains the session transcript as the evaluator's input. Evaluation outputs
   are redacted by the core's redactor; the shim itself is not, exactly like the raw Command
   Code JSONL it parallels.
7. **Hook covers sessions, not history.** Sessions that ended before the hook was installed
   are recovered with `scan --source hermes` / `hermes-session --session-id X`.
