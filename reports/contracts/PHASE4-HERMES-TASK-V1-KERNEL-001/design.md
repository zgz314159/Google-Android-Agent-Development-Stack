# Implementation Design — Phase-4 Hermes Task V1 control kernel install

## Architecture

The stack's orchestration layer already exists and is REUSED verbatim:

- `orchestration/hermes/bridge/` is the production home of the GPT <-> Hermes control kernel. It
  currently holds only the Phase-3 `chatgpt_adapter.py`.
- `orchestration/hermes/evidence/phase4-hermes-task-v1-kernel/bridge/` is the frozen Phase-4
  staging tree. It holds the complete, tested kernel: `protocol.py`, `bridge_state.py`,
  `contract_executor.py`, `bridge_cli.py`, `chatgpt_adapter.py` and `tests/` (unit suite plus an
  explicit READY-package dry run).
- `orchestration/hermes/evaluation_adapter/contract_guard.py` is the live fail-closed write guard.
  It is READ-ONLY here and is not modified by this change.
- `specification/compiler/` is the deterministic Specification Compiler that produced THIS package.
  It is READ-ONLY here and is not modified by this change.

This change adds no new architecture. It moves an existing, tested artifact from a staging
directory into its production directory, and it authorizes that one write surface.

What is REUSED and must not be rebuilt: the whole Phase-4 kernel (frozen), the Contract Guard, the
compiler, and the profile hook configuration. Nothing here is re-implemented.

Boundary note: the installed `orchestration/hermes/bridge/chatgpt_adapter.py` (Phase 3) differs
from the staged Phase-4 adapter. The install supersedes it; that is the single tracked overwrite.

## Data Flow

1. The install session is launched with `HERMES_CONTRACT_PACKAGE` pointing at this package, so the
   Contract Guard resolves its allow-list from `implementation-contract.json` here.
2. The session copies the staged kernel tree into `orchestration/hermes/bridge/`. Each copy is a
   path under `allowed_paths`, so the guard allows it.
3. The session runs the bridge unit suite from the installed location. Test discovery writes only
   `__pycache__` beneath the installed tree, which is inside the same allowed path.
4. The session computes sha256 for every staged and every installed kernel module and writes one
   parity record under the Phase-4 evidence directory.
5. The session stops. No bridge round is executed, no device is contacted, no profile hook is
   changed.

## File Structure Plan

**MUST TOUCH**

| File | Role | Expected change |
| --- | --- | --- |
| `orchestration/hermes/bridge/protocol.py` | kernel module (staged) | created from stage, byte-identical |
| `orchestration/hermes/bridge/bridge_state.py` | kernel module (staged) | created from stage, byte-identical |
| `orchestration/hermes/bridge/contract_executor.py` | kernel module (staged) | created from stage, byte-identical |
| `orchestration/hermes/bridge/bridge_cli.py` | kernel module (staged) | created from stage, byte-identical |
| `orchestration/hermes/bridge/chatgpt_adapter.py` | kernel module (staged) | overwritten from stage, byte-identical |
| `orchestration/hermes/bridge/tests/` | kernel test suite (staged) | created from stage, byte-identical |
| `orchestration/hermes/evidence/phase4-hermes-task-v1-kernel/` | Phase-4 evidence | parity report appended |

**MAY TOUCH**

| File | Role | Expected change |
| --- | --- | --- |
| `orchestration/hermes/bridge/__pycache__/` | bytecode cache | regenerated by the test run |

**MUST NOT TOUCH**

- `orchestration/hermes/evaluation_adapter/` — the frozen Contract Guard and its hooks.
- `specification/` — the compiler that generated this package.
- `verification/`, `verification-benchmark/` — Android verification layer and device lock.
- `orchestration/hermes/tools/` — finished WAVE1A proof tooling.
- `orchestration/hermes/HERMES-LOCK.json` — the pinned Hermes revision.
- `reports/contracts/` — every contract package, this one included.
- KeepLab product code, `Testapp/`, `PowerAi/` — out of scope for this stack change.

## Selector Contract

The compiler schema requires a selector contract even though this change touches no Android UI.
These entries are therefore **deterministic install identity markers**, not on-screen widgets: they
name the two filesystem states the install must be able to distinguish. The install performs zero
device interaction and zero visual judgment.

| name | state it identifies |
| --- | --- |
| `phase4_staged_kernel_source` | the staged Phase-4 kernel tree exists under the evidence directory |
| `phase4_bridge_kernel_installed` | the Phase-4 kernel tree exists under the production bridge directory |
